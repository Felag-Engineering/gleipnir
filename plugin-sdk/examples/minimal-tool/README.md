# minimal-tool

The smallest possible end-to-end ToolService plugin: one tool (`echo`), one
host RPC each of `GetInstanceConfig`, `EmitMetric`, and `Log`. If you are
writing your first Gleipnir plugin, start here.

## What this example demonstrates

- Declaring a `ToolService` and wiring a `hostv1.HostServiceClient` into it.
- Using `plugin-sdk/testing.NewFakeHost` for in-process tests — no real host binary required.
- The shape of a `manifest.Manifest` declaration in Go (`manifest.go`).
- A canonical `manifest.yaml` committed alongside the source and kept in sync by `TestManifestYAMLIsCanonical`.

## Layout

```
minimal-tool/
  main.go            — calls serve.Serve(); entry point for the plugin binary
  service.go         — ToolService with a single "echo" tool
  manifest.go        — pluginManifest variable (source of truth for metadata)
  manifest.yaml      — canonical YAML projection of manifest.go (generated, not hand-written)
  manifest_test.go   — TestManifestYAMLIsCanonical: round-trip + Go-source equality
  service_test.go    — TestEchoTool_Happy / _MalformedInput / _ListTools
  go.mod             — per-example module; resolved by the repo-root go.work
```

## Build

```sh
go build .
```

The produced binary currently panics if executed directly because `serve.Serve()`
is a Phase-3 stub. The implementation is tracked in issue #170. Use the test
suite (below) to exercise `ToolService` in-process today.

## Test

From the example directory:

```sh
go test .
```

Or, from the repo root via the workspace:

```sh
go test ./plugin-sdk/examples/minimal-tool/...
```

The four tests are:

| Test | What it asserts |
|------|----------------|
| `TestEchoTool_Happy` | Successful invocation: non-empty `output_json`, `echo_calls_total` metric emitted, `"echo handled"` log line written. |
| `TestEchoTool_MalformedInput` | Malformed JSON input produces an `ErrorEnvelope`; no metric is emitted. |
| `TestEchoTool_ListTools` | `ListTools` returns exactly one tool named `"echo"`. |
| `TestManifestYAMLIsCanonical` | `manifest.yaml` on disk round-trips through `manifest.Unmarshal` / `manifest.Marshal` without changing bytes, and equals `manifest.Marshal(&pluginManifest)` from `manifest.go`. |

`manifest_test.go` reads `manifest.yaml` with `os.ReadFile("manifest.yaml")` —
a relative path that works because `go test` runs with the package directory
as the working directory, so no special path setup is needed.

## Manifest

`manifest.go` is the source of truth. `manifest.yaml` is its canonical
projection — generated by `manifest.Marshal`, never written by hand.

If you edit `manifest.go`, regenerate the YAML with a throwaway helper. Create
`gen_manifest_local.go` in this directory (the `//go:build ignore` tag keeps
it out of normal builds):

```go
//go:build ignore

package main

import (
	"fmt"
	"os"

	"github.com/felag-engineering/gleipnir/plugin-sdk/manifest"
)

func main() {
	b, err := manifest.Marshal(&pluginManifest)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	os.Stdout.Write(b)
}
```

Then run (passing `manifest.go` so `go run` compiles it alongside the
helper — `pluginManifest` is declared there):

```sh
go run gen_manifest_local.go manifest.go > manifest.yaml
```

Delete `gen_manifest_local.go` before committing — the canonical `manifest.yaml`
is the artifact that lands in the repo. Run `go test .` afterwards to confirm
`TestManifestYAMLIsCanonical` still passes.

### gen-manifest and validate (blocked on #170)

`gleipnir-plugin gen-manifest` and `gleipnir-plugin validate` require the
plugin binary to implement the `--emit-manifest` flag, which is wired up by
`serve.EmitManifest`. That function is blocked on issue #170.

Until #170 lands, run `go test .` to verify the YAML stays in sync
(`TestManifestYAMLIsCanonical`).

Once #170 lands, the full workflow becomes:

```sh
go build -o minimal-tool .
gleipnir-plugin gen-manifest --binary ./minimal-tool --out manifest.yaml
gleipnir-plugin validate   --binary ./minimal-tool --manifest manifest.yaml
```

## Using outside the monorepo

This example's `go.mod` declares:

```
require github.com/felag-engineering/gleipnir/plugin-sdk v0.0.0
```

`v0.0.0` is a workspace-only pseudo-version. Inside the monorepo, the repo-root
`go.work` resolves it to the local `plugin-sdk/` directory automatically.

If you copy this example outside the monorepo you have two options:

1. Keep a `go.work` that points at a local checkout of `plugin-sdk`:

   ```
   go 1.22
   use ./plugin-sdk
   use ./my-plugin
   ```

2. Add a `replace` directive to your `go.mod`:

   ```
   replace github.com/felag-engineering/gleipnir/plugin-sdk => ../path/to/plugin-sdk
   ```

The `gleipnir-plugin new --sdk-replace` scaffold flag adds this `replace`
directive automatically when bootstrapping a new plugin outside the monorepo.
