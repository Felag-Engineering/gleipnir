# Settled architectural decisions — full statements

Moved verbatim from the root CLAUDE.md (2026-07-31), which now carries a compressed one-line-per-decision list. This file preserves the full operational statements; ADR bodies live in `ADR_Tracker.md`.

These are resolved constraints — do not re-litigate them.

- **Hard capability enforcement (ADR-001):** disallowed tools are never registered with the agent. Prompt-based restrictions are not a control mechanism and must not be used as one.
- **Policy stored as a YAML blob (ADR-002):** `name` and `trigger_type` are indexed columns for routing and list views; all other policy fields live in the `yaml` column. No separate data model for policy fields.
- **SQLite, WAL mode, no ORM (ADR-003):** WAL is enabled at the application layer on startup. Audit writes are serialized through an application-layer queue to avoid contention. All queries go through sqlc — raw `.sql` files only.
- **MCP HTTP transport only (ADR-004):** capability tags (`tool`/`feedback`) are Gleipnir's metadata, stored in Gleipnir's DB — not in the MCP server.
- **Package boundary:** `internal/mcp` must not import `internal/execution/agent`.
- **Policy-gated approval is a hard runtime guarantee (ADR-008):** tools marked `approval: required` are intercepted by the runtime before execution, regardless of agent reasoning.
- **Feedback channel resolution (ADR-009):** policy-level channel definition falls back to system-level config if absent.
- **SSE for real-time UI transport (ADR-016):** Server-Sent Events push run status changes, new steps, and approval events. Mutations remain REST. No WebSockets.
- **Policy-level parameter scoping (ADR-017):** tool parameters can be restricted per-policy via `params` blocks. Schema is narrowed before agent sees it — structural enforcement, not prompt-based.
- **Capability snapshot as first run step (ADR-018):** every run records the exact tools registered at run start.
- **Agent editor (ADR-019):** Form view is the only editing surface. YAML is the API payload and storage format; operators do not author it directly in the UI. YAML tab was removed in #751.
- **Policy folders are YAML-only (ADR-020):** `folder` is an optional string in the policy YAML for UI grouping. No DB column — purely cosmetic.
- **Model-agnostic design (ADR-026):** multi-provider support via `internal/llm` interface. Currently Anthropic + Google. Providers implement a common interface; agent runtime is provider-agnostic.
- **Tool risk classification (ADR-028):** tools categorized by risk level, affecting approval requirements.
- **Approval state machine (ADR-029):** minimal v1.0 approval lifecycle with timeout enforcement.
- **Protocol-agnostic tools page (ADR-030):** UI abstracts over tool transport. The Tools page does not expose MCP-specific concepts to users.
- **Native feedback (ADR-031):** feedback is a first-class runtime primitive. Agent can request operator input via `gleipnir.ask_operator`; the runtime manages the `waiting_for_feedback` state and timeout. User-facing term is **"Feedback request"** — the same flow as the audience-side "Request" routing (ADR-044); the UI labels both consistently (#656). Internal identifiers (`feedback_request`/`feedback_response` step types, `feedback` capability key, audience `request` field) are intentionally NOT renamed — deferred follow-up.
- **DB-backed system settings (ADR-035):** instance-level config (e.g. `public_url`) lives in a `system_settings` key/value table, editable via the admin UI at `/admin/system`. Admin-only `GET/PUT /api/v1/admin/settings` manages the table; a separate `GET /api/v1/config` endpoint (all authenticated roles) exposes non-sensitive values like `public_url` and `default_model` to operators and auditors.
- **Webhook secrets in encrypted DB column (ADR-034):** `webhook_secret_encrypted` is a dedicated column outside the YAML blob (scoped ADR-002 deviation). The `yaml` column is returned wholesale by GET /api/v1/policies/:id; storing a secret there would expose it to all authenticated roles. The `trigger.auth` mode (`hmac | bearer | none`) lives in YAML because it is configuration, not a secret. Auditors can see auth mode but cannot call the rotate/reveal endpoints (admin|operator only).
- **Atomic run-state transitions (ADR-038):** every status change runs in a transaction with a `version`-column CAS guard. Conflicts surface as `runstate.ErrTransitionConflict`; callers must not assume their write won.
- **Authenticated MCP servers (ADR-039):** `mcp_servers` rows may carry encrypted static auth headers (`auth_headers_encrypted` TEXT column) injected on every outbound MCP request. Values are write-only over the API — `GET` returns header *keys* only. Individual headers are managed via `PUT`/`DELETE /api/v1/mcp/servers/:id/headers/:name` (admin|operator); bulk `PUT /:id` does NOT touch credentials (mirrors ADR-034 webhook-secret pattern). Reserved headers (`Mcp-Session-Id`, `Mcp-Method`, `Mcp-Name`, `Mcp-Protocol-Version`, `Content-Type`, `Accept`, `Content-Length`, `Host`) are rejected by validation. Per-policy and per-user credential scoping are explicitly deferred. `internal/mcp` imports `internal/admin` for in-registry decryption.
- **Arcade gateway pre-authorization (ADR-040):** Arcade MCP servers are detected by URL + header heuristic (`internal/arcade.IsArcadeGateway`). Toolkits are pre-authorized one click at a time via Arcade's `/v1/auth/authorize` REST API. No DB schema changes — credentials reuse `auth_headers_encrypted` from ADR-039. The `/wait` endpoint uses a 10s Arcade wait window; the frontend loops until terminal so each request stays under `GLEIPNIR_HTTP_WRITE_TIMEOUT`. Per-policy user_id and runtime auth-required handling are explicitly deferred.
- **Plugin observability surface (ADR-047):** Plugin-emitted metrics are force-prefixed `gleipnir_plugin_` and auto-labelled with `plugin`/`instance`; per-(metric, label-key) cardinality is hard-capped at 100 distinct values with loud `ResourceExhausted` rejection (not silent drop) so misconfigured high-cardinality labels surface in dev. Plugin logs ride the `Log` host RPC over gRPC/UDS rather than stdout — gRPC carries `call_id`/`run_id`/`policy_id` correlation through `internal/infra/logctx`, while stdout has no ordering or attribution guarantees. Stderr capture remains as the fallback for detached calls and pre-handshake panics; stdout is reserved by go-plugin for the handshake magic-cookie. Bucket presets reuse `internal/infra/metrics` (`BucketsFast`/`BucketsSlow`); lifecycle events ride `internal/infra/event.Publisher`. OpenTelemetry is explicitly deferred to v2.
- **Redact-on-read for plugin instance config secret fields (ADR-049):** Plugin manifest properties annotated with `x-gleipnir-secret: true` (SDK: `manifest.SecretString` typed field) are redacted to `"***"` on every GET response for the instance config endpoint. The host detects the annotation via `internal/plugin/configvalidate.SecretPropertyNames`. The bulk PUT (`PUT .../config`) rejects `"***"` as a value for secret fields to prevent round-trip clobber. A per-field write-only PUT (`PUT .../config/{property}`) mirrors the ADR-039 `PUT /mcp/servers/:id/headers/:name` pattern. GET returns 500 when the manifest cannot be parsed (fail-closed per the ADR-001 posture). Both write handlers apply redaction in the fallback synthesized-response path as well. Storage shape is unchanged — `config_json` still holds the raw value, which is already encrypted at rest. Generalizes ADR-034 (webhook secrets) and ADR-039 (MCP auth headers) to plugin instance config.
- **Plugin system architecture (ADR-041):** HashiCorp go-plugin subprocesses speaking gRPC over UDS, parallel to MCP. Three capability surfaces (ToolService, ChannelService, TriggerService). Plugin tools and MCP tools share one `<source>.<tool>` namespace via `internal/toolregistry`. Hard capability enforcement (ADR-001) applies identically. Distribution is filesystem dropin only; no curated registry.
- **Plugin service versioning (ADR-042):** Per-service SemVer on four independent axes (TriggerService, ToolService, ChannelService, HostAPI). Two-major-version deprecation window for removals. New enum values are additive (plugins handle mandatory `UNKNOWN = 0`). `buf lint` enforces structural compatibility in CI.
- **Plugin signing tooling (ADR-043):** Bundled Minisign Go library in `plugin-sdk/signing` for signing and verification. Surfaced via `gleipnir-plugin keygen|sign|package` CLI subcommands. No external `minisign` binary dependency.
- **Channel routing model (ADR-044):** Two channel operations: `Notify` (fire-and-forget, parallel fan-out, 10s deadline) and `Request` (exactly-one routing, async callback via `WriteAuditStep`). Audiences are named, ordered, admin-managed channel-entry lists referenced by policy YAML. `gleipnir.in-app` is auto-appended as lowest-priority fallback unless explicitly disabled. Six credential strategies (none, static_api_key, header_set, basic_auth, oauth2_authcode, oauth2_clientcred). Partially supersedes ADR-031 (dispatcher implementation, not the first-class-feedback principle). A third best-effort host→plugin RPC, `ChannelService.RequestTerminated` (#625), notifies the owning plugin when a Request reaches a terminal state (approved/rejected/answered/timed_out; canceled/superseded reserved) so it can close the loop in the channel UI (e.g. Slack `chat.update` to a resolved summary, buttons removed). Host-initiated timeouts fire it from the channel dispatcher / plugin-request scanner; operator resolutions are closed by the plugin's own callback path. Non-implementing plugins return `codes.Unimplemented`, treated as a no-op.
- **Plugin signing & TOFU trust (ADR-045):** Minisign tamper-evidence with TOFU pubkey pinning at first install. Updates must verify against the pinned key; key rotation requires admin approval via "Accept new key" flow. Material manifest changes block hot-reload pending admin re-approval. `GLEIPNIR_ALLOW_UNSIGNED_PLUGINS` is the global escape hatch for development. Identity attestation (Sigstore) deferred to v2.
- **Audit-table split (ADR-046):** `run_steps` carries LLM-visible operations (replayed into agent context); `plugin_audit_events` carries operational/admin/security events (never enters agent context). `WriteAuditStep` Host RPC restricted to `feedback_response` step type only; all other plugin events are host-written into `plugin_audit_events`.
- **Subscribed trigger type (ADR-048):** Internal-only trigger type name for plugin-sourced events. Policies bind to a `(source, event_kind)` pair from an installed plugin's manifest. Binding filters use typed form fields (regex, contains, equals) from `binding_schema`, not JSONPath. UI renders plugin event kinds as peer options alongside built-in trigger types; the word "subscribed" is never shown to operators.
- **Dispatcher separation (ADR-051):** the plugin tool-call pool (`dispatch/pool.go`), channel Notify/Request dispatcher (`dispatch/channel.go`), and trigger-event dispatcher (`trigger/dispatcher.go`) are intentionally separate — different routing keys, concurrency models, and persistence; identity/generation gating lives in the hostsvc interceptor layer, not in any dispatcher. Do not merge them into one routing module.
- **Operator-selectable binding operators (ADR-052):** A plugin trigger field may advertise a SET of allowed match operators (`contains`/`regex`/`equals`) in its `binding_schema`; the operator picks one per policy via a matcher dropdown in the policy editor. Wire format is back-compatible: a flat `field: value` binding means "the field's author-declared default operator" (preserving every existing flat binding, including the just-shipped `text`/`text_regex`/`channel_type`/`user`/`mention_only` sibling fields), and `field: {op: regex, value: "..."}` is the explicit per-policy override. The operator is resolved per-policy, not from schema shape. `mention_only` stays a fixed-semantic reserved field (not operator-selectable). Decided direction; implementation deferred to follow-ups. Do not re-litigate operator selectability.
- **MCP 2026 realignment (ADR-053…ADR-060, target tag `v0.2.0-alpha` — decided 2026-07-30, NOT yet implemented):** the gRPC plugin substrate will be replaced outright (hard cutover, no dual-running) by plugins-as-signed-containerized-MCP-servers with a capability-profile model; event triggering moves to the `io.gleipnir/events` MCP extension (events are host-captured control-plane — never injected into model context; payloads may enter prompts only via explicit policy templating as untrusted data); tool-initiated HITL rides MRTR + the Tasks extension through audiences (distinct from the ADR-008 gate; per-run elicitation budget, size caps, per-server rate limit); container substrate uses the runtime socket (rootless Podman recommended, manual-compose escape hatch) with one internal network per instance and manifest-declared egress; host API stays for managed plugins over network + instance token; user scoping = verified identity linking + user_config_schema (per-user credentials deferred); LLM schema policy = lossy presentation, exact enforcement. Full body: `docs/developer/mcp-realignment-spec.md`. Until implementation lands, the v1.1 plugin architecture described elsewhere in this file remains the live system — do not mix the two.
- **CSS Modules, no inline styles:** All frontend styling goes through CSS Modules consuming CSS custom properties. No inline `style={}` attributes.
- **4px spacing scale:** All margins, padding, and gaps snap to multiples of 4px (4, 8, 12, 16, 24, 32, 48, 64).
